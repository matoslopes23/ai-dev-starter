# Referências primárias e uso no kit

Consultadas em 2026-11-08. Estes links apoiam decisões; não são cópias de normas nem promessa de conformidade. Verifique revisões e requisitos específicos quando aplicar no produto. Os procedimentos do kit são uma síntese própria e adaptável.

| Fonte | Como orienta o kit |
|---|---|
| [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow) | Branches, revisão e integração de mudanças |
| [Gitflow — texto original e reflexão do autor](https://nvie.com/posts/a-successful-git-branching-model/) | Política para releases; avaliar adequação antes de adotar |
| [DORA: trunk-based development](https://dora.dev/capabilities/trunk-based-development/) | Lotes pequenos e integração frequente |
| [GitHub: protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) | Proteções efetivas além de templates |
| [NIST SSDF, SP 800-218, versão 1.1 final](https://csrc.nist.gov/pubs/sp/800/218/final) | Segurança integrada ao ciclo de desenvolvimento |
| [OWASP ASVS](https://asvs.owasp.org/) | Requisitos verificáveis de segurança de aplicações |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | Critérios de acessibilidade web |
| [OpenTelemetry: sinais](https://opentelemetry.io/docs/concepts/signals/) | Métricas, logs e traces na observabilidade |

Clean Architecture, SOLID, DRY, KISS e YAGNI são usados como heurísticas de design. O kit não mede adesão por quantidade de camadas/classes e não exige uma implementação canônica desses conceitos. As decisões devem demonstrar melhoria na mudança, teste ou operação da aplicação concreta.
